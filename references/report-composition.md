# 报告组合引擎：按目的选模块，再把模块连接到回答

报告不是将所有章节依次拼接。先确定用户完成后想获得的答案，再组合**设定层 + 分析层 + 数据层 + 行动层 + 页面结构**。目录在 `assets/report-recipes.json`，用 `scripts/compose-report.cjs` 可查看某类初始组合。

8类配方是可扩展的示例，不是范围上限。根据答题者希望获得的答案，自主提出新目的、新模块或混合结构；每个新增模块仍需定义回答/资料需求、图形、解释边界和替代内容。若使用脚本，先更新项目内目录并验证新ID，不强行套用不适合的旧类型。

## 1. 选择主目的，可配副目的

心理/行为模式探索：情境与模式、作用与代价、条件化的形成线索、当下影响、后续场景和改变方向。

历史人物/角色相似：结果身份、多维相似度、相似/不相似、相邻人物、情境对照、时代/角色边界、可借鉴部分。

动物/虚构设定：人格化比喻、行为偏好、组合特征、故事与应用；比喻不能冒充动物学或人格科学。

职业/路径：主副线、适配和冲突、进入条件、不同阶段及可选行动。

偏好与生活方式：选择轮廓、情境满足、负担与推荐组合。知识类：正确性、误区与学习路径。决策类：目标、比较矩阵、约束和取舍。

混合主题如“你像哪位历史人物，以及适合怎样工作”需指定主目的，并分别研究人物档案和职业事实，不将一方的分数直接当另一方结论。

## 2. 设定层独立于判断层

设定可用人物、动物、植物、物品、地点、旅程或无角色的抽象风格。为每个结果保存 settingId、名称、原创/史实/授权状态、图像权利、隐喻含义和不应推断的内容。

换一张动物图、换人物外观，不改变分数。历史人物的名称不是装饰性随意匹配：需建独立人物档案，按维度保存可定位材料、相反事例和解释的不确定性，不把现代人格标签当史实。

## 3. 每个模块的内容合同

每区写清：它回答用户什么、读哪些 answers/dimensions/context、用哪些 claims、输出什么图、如何生成差异化分析、何时采用替代模块。先在方案里给**样例内容**和数据来源位置，用户确认后写渲染。

完整解释至少有一条跨题联系：例如价值愿望与过程代价相冲突、相同行为在不同动机下意义不同、某优势在特定条件下有代价。不得只把选择次数换成“潜意识分数”，也不让所有类型共用同一段话。

模块还需有 `certainty`：自述事实、规则计算、文献中的群体关联、解释假设、条件化情境或比喻。叙述力度跟着依据走。

## 4. 过去、当下、未来如何写

- **过去**：用户明确报告的经历可按“你提到……”关联到当前模式；文献支持的普遍机制只能列为几种可能解释，不能写成“你小时候一定经历了……”。不靠选择题反推被遗忘事件或疾病。
- **形成阶段**：先收集生活阶段和外部条件，讨论何种压力/环境可能触发；不设“某年龄必然形成”的无证据模板。
- **当下**：连接用户报告的行为、目标、短期收益与成本。把功能和消耗都讲清楚，避免给用户贴缺陷标签。
- **未来**：写“如果条件持续”“如果改变某条件”的分支，区分可能影响与必然预测；没有纵向数据不画虚构成长曲线。
- **改善**：给对应模式的小而可调整的方向；不承诺治愈，不以临床建议替代合格专业服务。具体健康建议需按主题查证。

需要更多个人经历时，将必要且适当的问题放在前测，允许不愿提供；结果阶段不再次要求填表。缺少历史自述时，自动改为“可能的触发条件/保护作用”而非留空、指责用户未完成或编造过去。

## 5. 百分比不共用一套含义

**探索指数**可以用原有题目加分归一化，但只能解释为该规则下的倾向。

**人物相似性**可用透明的加权距离：同范围维度先归一化为0–1，similarity = 100 × [1 − Σ(w×abs(user−profile))/Σw]。维度方向、权重、人物档案的编码理由和数据缺失必须明确；档案分数是有材料约束的研究者解释，不是人物真实人格测量。至少列出相似和不同；相邻候选接近就显示接近，不称唯一命中。

**知识测试**的正确率必须有明确答案与题目权重；**职业匹配**需将偏好适配、过程耐受和进入条件分开解释。不能把一种分数的标题换掉就用于所有主题。

## 6. 图形和分析搭配

模块不是“标题+一图”就完成。规范顺序：短结论 → 图/场景 → 2–3条回答支持 → 组合解读 → 代价/限制 → 下一步。图形仅在支持决策时出现，叙述型模块可用分镜、循环图、双栏或条件分叉。

心理探索中重点可视化模式差异与情境链，避免仪表盘伪造病情；历史相似中重点可比维度、相邻人物条形、相似/差异矩阵，避免用饼图将独立相似度凑满100%。

## 7. 组合器发挥作用的方式

在方案阶段：自动推荐主目的、候选设定、模块顺序、每区需要的题目/资料与数据图，给作者确认。

在原型阶段：把蓝图变为有样例答案和完整报告的页面。每个模块保留自己的输入字段和适用条件，而不硬编码一个通用长报告。

在答题结果阶段：根据实际回答与可用数据选择分支/替代内容，生成完整报告。`compose-report.cjs` 是蓝图与适用性参考，不是自动生成临床解释的内容模型；AI仍须实现并验证具体题库与叙述规则。

在审查阶段：检查每一模块的输入是否存在、是否真的改变解释、是否把关联说成因果、有没有设定与评分脱节。对于组合变化，用不同动机/条件但表面行为相同的回答路径作对照。

## 面向测试用户的报告边界

消费者报告只展示结果、必要图形、个性化分析、匹配与差异、影响和建议。不展示数据出处、参考文献、来源链接、检索记录、公式、权重、计分过程、方法论、资料覆盖率或作者设计思路。这些保存在独立的作者研究与审查文件中。

区分“解释你的模式为什么发生”和“解释系统怎样计算结果”：前者保留，后者不进入消费者报告。保留图形的必要标签、单位及简短的分数含义；不因省略方法就把可能解释写成确定因果。网页、打印及HTML/TXT/PDF导出采用同一边界，不能仅靠CSS隐藏。审查时核对代表结果及导出内容。作者方案评审和教学图集可展示内部方法，不作为消费者报告。
